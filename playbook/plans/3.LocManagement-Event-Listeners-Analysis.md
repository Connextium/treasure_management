# LocManagement & Loc Smart Contract Event Listener Analysis

## Overview
This document provides a comprehensive analysis of event logs emitted by the `LocManagement` and `Loc` smart contracts, with implementation guidance for event listeners using Chainlink CRE SDK's `logTrigger` capability.

**Analysis Date**: February 1, 2026  
**Document Version**: 3.0  
**Contracts Analyzed**:
- `LocManagement.sol` - Main LC management orchestrator
- `Loc.sol` - Individual LC contract instances

---

## Executive Summary

### Monitoring Strategy: Dual-Contract Event Tracking

**PRODUCTION REQUIREMENT**: Monitor **BOTH** LocManagement and individual Loc contracts

### Why Both Contracts Must Be Monitored

🔴 **CRITICAL**: The Loc contract design allows sellers to call `settleLC()` **directly**, bypassing LocManagement entirely.

**Dual Access Paths**:
1. **Orchestrated**: User → LocManagement → Loc (both contracts emit events)
2. **Direct**: Seller → Loc (only Loc emits events)

**Consequence**: Monitoring only LocManagement = **MISSING direct operations**

### Contract Event Architecture
- **LocManagement**: 5 events tracking LC lifecycle at management level
- **Loc**: 4 events tracking LC operations at individual LC level
- **Total**: 9 distinct event types for comprehensive LC monitoring
- **All 9 events required** for complete visibility

---

## ⚠️ CRITICAL ARCHITECTURE NOTE: Direct Access Pattern

### The Problem: Dual Access Paths

The Loc contracts are designed with **two access paths** for certain operations:

#### Path 1: Through LocManagement (Orchestrated)
```
User/System → LocManagement.settleLC() → Loc.settleLC()
Events Emitted: 
  ✅ LocManagement.LCSettled (locNo)
  ✅ Loc.LocSettled (locNo, beneficiary, amount, timestamp)
```

#### Path 2: Direct to Loc Contract (Bypasses LocManagement)
```
Seller → Loc.settleLC() DIRECTLY
Events Emitted:
  ❌ LocManagement.LCSettled (NOT EMITTED!)
  ✅ Loc.LocSettled (locNo, beneficiary, amount, timestamp)
```

### Why Direct Access Exists

**From Loc.sol:**
```solidity
function settleLC() public {
    require(msg.sender == locData.sellerAcc || msg.sender == owner(), 
            "Loc: caller is not the seller or owner");
    // Seller can call directly!
}
```

**Implications:**
- ✅ Sellers have autonomy to settle without central authority
- ✅ Reduces dependency on LocManagement availability
- ⚠️ **Monitoring only LocManagement events = INCOMPLETE tracking**
- ⚠️ **Must monitor individual Loc contracts to catch all operations**

### Other Direct-Callable Functions

Similar pattern may exist for:
- `expireLC()` - Only owner, but could be called on Loc directly
- `activateLC()` - Only owner (LocManagement)

### Monitoring Impact

**If you only monitor LocManagement:**
- ❌ **MISS all direct seller settlements**
- ❌ Incomplete audit trail
- ❌ Incorrect settlement statistics
- ❌ Missed notifications to parties

**If you monitor both LocManagement AND Loc:**
- ✅ Capture ALL operations (orchestrated + direct)
- ✅ Complete audit trail
- ✅ Can identify operation patterns
- ✅ Differentiate between access paths

**Conclusion: Monitoring BOTH is REQUIRED for production systems.**

## Contract Event Inventory

### 1. LocManagement Contract Events

#### Event 1: `LCIssued`
```solidity
event LCIssued(
    uint256 indexed locNo,
    address indexed buyerAcc,
    address indexed sellerAcc,
    uint256 amount,
    address locContractAddress
);
```

**Trigger Point**: When a new Letter of Credit is issued  
**Function**: `issueLC()`  
**Emitted By**: LocManagement contract  
**Access Control**: `onlyIssuingBank` modifier

**Event Data**:
- `locNo` (indexed): Unique LC number identifier
- `buyerAcc` (indexed): Buyer's account address
- `sellerAcc` (indexed): Seller/beneficiary account address
- `amount`: LC amount value
- `locContractAddress`: Address of the newly created Loc contract

**Use Cases**:
- Track new LC creation in real-time
- Update LC registry/database
- Notify buyer and seller of LC issuance
- Monitor LC creation patterns and volumes
- Trigger downstream workflows (compliance checks, notifications)

**Priority**: 🔴 **CRITICAL** - Entry point for all LC lifecycles

---

#### Event 2: `LCActivated`
```solidity
event LCActivated(uint256 indexed locNo);
```

**Trigger Point**: When LC is activated and funds are allocated  
**Function**: `activateLC()`  
**Emitted By**: LocManagement contract  
**Access Control**: `onlyIssuingBank` modifier

**Event Data**:
- `locNo` (indexed): LC number

**Related Operations**:
- Funds minted to issuing bank via TreasureLedger
- `LCFundsMinted` event also emitted
- Individual Loc contract activated

**Use Cases**:
- Confirm LC is ready for settlement
- Monitor fund allocation timing
- Trigger seller notification that LC is active
- Update LC status dashboards
- Track LC activation rates

**Priority**: 🟠 **HIGH** - Indicates LC is operational

---

#### Event 3: `LCFundsMinted`
```solidity
event LCFundsMinted(
    uint256 indexed locNo, 
    address indexed issuingBank, 
    uint256 amount
);
```

**Trigger Point**: When LC funds are minted to issuing bank  
**Function**: `activateLC()`  
**Emitted By**: LocManagement contract  
**Access Control**: `onlyIssuingBank` modifier

**Event Data**:
- `locNo` (indexed): LC number
- `issuingBank` (indexed): Issuing bank address receiving funds
- `amount`: Amount minted

**Use Cases**:
- Audit trail for fund creation
- Monitor issuing bank fund allocation
- Reconcile TreasureLedger balances
- Detect unusual minting patterns
- Compliance and regulatory reporting

**Priority**: 🟠 **HIGH** - Financial tracking critical

---

#### Event 4: `LCSettled`
```solidity
event LCSettled(uint256 indexed locNo);
```

**Trigger Point**: When LC is successfully settled  
**Function**: `settleLC()`  
**Emitted By**: LocManagement contract  
**Access Control**: Seller or contract owner

**Event Data**:
- `locNo` (indexed): LC number

**Related Operations**:
- Funds transferred from issuing bank to seller
- Individual Loc contract marked as settled

**Use Cases**:
- Confirm successful LC completion **via LocManagement**
- Trigger payment confirmation notifications
- Update settlement statistics
- Close out LC records
- Generate settlement reports
- Release buyer from obligations

⚠️ **IMPORTANT**: This event is **ONLY** emitted when settlement goes through LocManagement. Direct settlements by sellers to Loc contracts will **NOT** emit this event. You **MUST** also monitor `Loc.LocSettled` events.

**Priority**: 🟠 **HIGH** - But insufficient alone; must combine with Loc.LocSettled

---

#### Event 5: `LCExpired`
```solidity
event LCExpired(uint256 indexed locNo);
```

**Trigger Point**: When LC expires without settlement  
**Function**: `expireLC()`  
**Emitted By**: LocManagement contract  
**Access Control**: `onlyIssuingBank` modifier

**Event Data**:
- `locNo` (indexed): LC number

**Related Operations**:
- Individual Loc contract marked as expired
- Funds not transferred (remain with issuing bank)

**Use Cases**:
- Monitor expired LCs
- Trigger expiry notifications to parties
- Update LC status to expired
- Analyze expiry patterns
- Handle fund recovery/return processes
- Alert issuing bank for fund release

**Priority**: 🟡 **MEDIUM** - Exception handling

### 2. Loc Contract Events (Individual LC Instances)

Each deployed Loc contract emits its own events. These provide granular detail at the individual LC level.

#### Event 6: `LocActivated`
```solidity
event LocActivated(uint256 indexed locNo, uint256 timestamp);
```

**Trigger Point**: When individual LC contract is activated  
**Function**: `activateLC()`  
**Emitted By**: Individual Loc contract  
**Access Control**: Only contract owner (LocManagement)

**Event Data**:
- `locNo` (indexed): LC number
- `timestamp`: Activation timestamp

**Use Cases**:
- Granular timestamp tracking
- Cross-validate with LocManagement activation
- Audit individual LC state changes

**Priority**: 🟢 **LOW** - Duplicate of LocManagement.LCActivated (if monitoring both)

---

#### Event 7: `LocSettled`
```solidity
event LocSettled(
    uint256 indexed locNo, 
    address indexed beneficiary, 
    uint256 amount, 
    uint256 timestamp
);
```

**Trigger Point**: When individual LC is settled  
**Function**: `settleLC()`  
**Emitted By**: Individual Loc contract  
**Access Control**: Seller or owner

**Event Data**:
- `locNo` (indexed): LC number
- `beneficiary` (indexed): Seller receiving funds
- `amount`: Settlement amount
- `timestamp`: Settlement timestamp

**Use Cases**:
- **PRIMARY SOURCE** for all settlement tracking
- Captures **direct settlements** by sellers (bypassing LocManagement)
- Detailed settlement information with beneficiary and amount
- Precise settlement timestamp
- Financial reconciliation
- Cross-validate with LocManagement settlement (when orchestrated)

⚠️ **CRITICAL**: This is the **ONLY** event emitted when sellers settle directly. Monitoring this is **REQUIRED** for complete settlement tracking.

**Priority**: 🔴 **CRITICAL** - Only reliable source for ALL settlements (direct + orchestrated)

---

#### Event 8: `FundsReleased`
```solidity
event FundsReleased(
    address indexed recipient, 
    uint256 amount, 
    uint256 timestamp
);
```

**Trigger Point**: When funds are transferred to seller  
**Function**: `settleLC()`  
**Emitted By**: Individual Loc contract  
**Access Control**: Seller or owner

**Event Data**:
- `recipient` (indexed): Seller receiving funds
- `amount`: Amount transferred
- `timestamp`: Transfer timestamp

**Use Cases**:
- Track actual fund transfers
- Payment confirmation
- Audit trail for fund movement
- Reconcile with TreasureLedger transfers

**Priority**: 🟢 **LOW** - Emitted alongside LocSettled

---

#### Event 9: `LocExpired`
```solidity
event LocExpired(uint256 indexed locNo, uint256 timestamp);
```

**Trigger Point**: When individual LC expires  
**Function**: `expireLC()`  
**Emitted By**: Individual Loc contract  
**Access Control**: Only owner (LocManagement)

**Event Data**:
- `locNo` (indexed): LC number
- `timestamp`: Expiry timestamp

**Use Cases**:
- Precise expiry timestamp
- Cross-validate with LocManagement expiry

**Priority**: 🟢 **LOW** - Duplicate of LocManagement.LCExpired (if monitoring both)

## Implementation Strategy

### Dual-Contract Monitoring Approach

**Why This is REQUIRED**:
- 🔴 **CRITICAL**: Sellers can call `Loc.settleLC()` **directly**, bypassing LocManagement
- 🔴 **CRITICAL**: Monitoring only LocManagement = **MISSING direct settlements**
- ✅ Complete visibility into ALL LC operations (orchestrated + direct)
- ✅ Differentiate between LocManagement-mediated vs direct operations
- ✅ Maximum detail and validation
- ✅ Cross-reference between contracts for verification
- ✅ Detailed audit trail with timestamps and amounts
- ✅ Individual LC-level granularity

### Events to Monitor

**From LocManagement (Central Orchestrator)**:
1. 🔴 `LCIssued` - **CRITICAL**: Track new LC creation, get Loc contract addresses
2. 🟠 `LCFundsMinted` - Fund allocation tracking
3. 🟢 `LCActivated` - Management-level activation (supplementary)
4. 🟢 `LCSettled` - Management-level settlement (only for orchestrated calls)
5. 🟢 `LCExpired` - Management-level expiry (supplementary)

**From Individual Loc Contracts (Primary Operations)**:
6. 🟡 `LocActivated` - Detailed activation with timestamp
7. 🔴 `LocSettled` - **CRITICAL**: Captures ALL settlements (direct + orchestrated)
8. 🟠 `FundsReleased` - Actual fund transfer confirmation
9. 🟡 `LocExpired` - Detailed expiry with timestamp

### Implementation Steps

**Step 1: Track Loc Contract Creation**
- Listen to `LocManagement.LCIssued` events
- Extract `locContractAddress` from event
- Dynamically register event listeners for each new Loc contract

**Step 2: Monitor Individual Loc Contracts**
- For each Loc contract address, listen to all Loc events
- Primary focus: `LocSettled` (captures direct + orchestrated)
- Secondary: `LocActivated`, `LocExpired`, `FundsReleased`

**Step 3: Correlate Events**
- Track both LocManagement and Loc events per LC number
- Identify orchestrated operations (both events present)
- Identify direct operations (only Loc events present)
- Flag discrepancies for investigation

### Implementation Considerations

**Complexity**:
- ⚠️ Requires dynamic subscription to new Loc contracts as they're created
- ⚠️ More complex event listener management
- ⚠️ Higher resource consumption
- ✅ This complexity is **necessary** for complete tracking

**Alternative (Not Recommended)**:
If you modify `Loc.settleLC()` to remove `msg.sender == locData.sellerAcc`, you could monitor only LocManagement. However, this:
- ❌ Reduces seller autonomy
- ❌ Increases dependency on LocManagement availability
- ❌ May violate business requirements

## CRE Workflow Integration

### Workflow Structure

```typescript
// locmgmt-workflow/main.ts
import { 
  LogCapability, 
  handler, 
  Runner, 
  type Runtime 
} from "@chainlink/cre-sdk";
import { lcIssuedListener } from "./eventListeners/lcIssuedListener";
import { lcActivatedListener } from "./eventListeners/lcActivatedListener";
import { lcSettledListener } from "./eventListeners/lcSettledListener";
import { lcExpiredListener } from "./eventListeners/lcExpiredListener";
import { lcFundsMintedListener } from "./eventListeners/lcFundsMintedListener";

type Config = {
  locManagementAddress: string;
  rpcUrl: string;
  chainId: number;
};

const initWorkflow = (config: Config) => {
  const log = new LogCapability();

  return [
    // LC Issued Event
    handler(
      log.trigger({
        address: config.locManagementAddress,
        topics: [
          "0x" + keccak256("LCIssued(uint256,address,address,uint256,address)").toString("hex")
        ],
      }),
      lcIssuedListener
    ),
    
    // LC Activated Event
    handler(
      log.trigger({
        address: config.locManagementAddress,
        topics: [
          "0x" + keccak256("LCActivated(uint256)").toString("hex")
        ],
      }),
      lcActivatedListener
    ),
    
    // LC Funds Minted Event
    handler(
      log.trigger({
        address: config.locManagementAddress,
        topics: [
          "0x" + keccak256("LCFundsMinted(uint256,address,uint256)").toString("hex")
        ],
      }),
      lcFundsMintedListener
    ),
    
    // LC Settled Event
    handler(
      log.trigger({
        address: config.locManagementAddress,
        topics: [
          "0x" + keccak256("LCSettled(uint256)").toString("hex")
        ],
      }),
      lcSettledListener
    ),
    
    // LC Expired Event
    handler(
      log.trigger({
        address: config.locManagementAddress,
        topics: [
          "0x" + keccak256("LCExpired(uint256)").toString("hex")
        ],
      }),
      lcExpiredListener
    ),
  ];
};

export async function main() {
  const runner = await Runner.newRunner<Config>();
  await runner.run(initWorkflow);
}
```

## Event Listener Implementation Templates

### Template 1: LC Issued Listener

```typescript
// locmgmt-workflow/eventListeners/lcIssuedListener.ts
import { type Runtime, type EVMLog, bytesToHex } from "@chainlink/cre-sdk";
import { decodeEventLog } from "viem";
import { type Config } from "../config";
import { locManagementAbi } from "../abis/locManagementAbi";

export interface LCIssuedData {
  locNo: bigint;
  buyerAcc: `0x${string}`;
  sellerAcc: `0x${string}`;
  amount: bigint;
  locContractAddress: `0x${string}`;
  txHash: string;
  blockNumber: bigint;
}

export function lcIssuedListener(
  runtime: Runtime<Config>, 
  payload: EVMLog
): LCIssuedData {
  runtime.log("━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━");
  runtime.log("LC Management: LCIssued Event Detected");
  runtime.log("━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━");

  try {
    // Step 1: Decode event log
    const topics = payload.topics.map(
      (t) => bytesToHex(t) as `0x${string}`
    ) as [`0x${string}`, ...`0x${string}`[]];
    const data = bytesToHex(payload.data);

    const decodedLog = decodeEventLog({
      abi: locManagementAbi,
      topics,
      data,
    });

    const { locNo, buyerAcc, sellerAcc, amount, locContractAddress } = 
      decodedLog.args as {
        locNo: bigint;
        buyerAcc: `0x${string}`;
        sellerAcc: `0x${string}`;
        amount: bigint;
        locContractAddress: `0x${string}`;
      };

    runtime.log(`[Event] LC Number: ${locNo}`);
    runtime.log(`[Event] Buyer: ${buyerAcc}`);
    runtime.log(`[Event] Seller: ${sellerAcc}`);
    runtime.log(`[Event] Amount: ${amount.toString()}`);
    runtime.log(`[Event] Loc Contract: ${locContractAddress}`);

    // Step 2: Extract transaction context
    const txHash = bytesToHex(payload.txHash);
    runtime.log(`[Tx] Hash: ${txHash}`);
    runtime.log(`[Tx] Block: ${payload.blockNumber}`);

    // Step 3: Business logic
    // - Update database
    // - Send notifications to buyer and seller
    // - Trigger compliance checks
    // - Update analytics dashboards

    const lcData: LCIssuedData = {
      locNo,
      buyerAcc,
      sellerAcc,
      amount,
      locContractAddress,
      txHash,
      blockNumber: payload.blockNumber,
    };

    runtime.log("━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━");
    return lcData;
  } catch (err) {
    const msg = err instanceof Error ? err.message : String(err);
    runtime.log(`[ERROR] ${msg}`);
    runtime.log("━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━");
    throw err;
  }
}
```

## Conclusion

### Implementation Summary

**PRODUCTION REQUIREMENT**: Dual-Contract Event Monitoring

**Why This Approach is Required**:
- 🔴 **Sellers can call Loc contracts directly**, bypassing LocManagement
- 🔴 Single-contract monitoring = **Missing direct settlements**
- 🔴 Incomplete audit trail and inaccurate statistics
- 🔴 Potential regulatory and compliance violations

**What This Delivers**:
- ✅ Complete visibility into ALL LC operations
- ✅ Captures both orchestrated (via LocManagement) and direct (to Loc) operations
- ✅ Detailed event data with timestamps, beneficiaries, and amounts
- ✅ Ability to identify operation patterns and access paths
- ✅ Full audit trail for compliance
- ✅ Differentiation between orchestrated and direct operations

**Implementation Requirements**:
- ⚠️ Dynamic registration of Loc contract listeners as LCs are created
- ⚠️ Event correlation logic to match LocManagement and Loc events
- ⚠️ Higher resource consumption than single-contract approach
- ✅ This complexity is **necessary and justified** for production systems

**Alternative Option**:
If dual-contract monitoring is unacceptable, you must:
1. Modify Loc contracts to **remove** seller's direct access (`msg.sender == locData.sellerAcc`)
2. Enforce ALL operations through LocManagement only
3. Accept reduced seller autonomy and increased LocManagement dependency

### Success Criteria

- ✅ All LC lifecycle events captured (including direct calls)
- ✅ Real-time event processing (< 30s latency)
- ✅ 99.9% event detection reliability
- ✅ Comprehensive error handling and recovery
- ✅ Complete audit trail for compliance
- ✅ Differentiation between orchestrated and direct operations
- ✅ Dynamic Loc contract discovery and monitoring
